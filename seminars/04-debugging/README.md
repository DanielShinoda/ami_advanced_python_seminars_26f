# Семинар 4 — отладка

Лекция показала `pdb` в интерактивном режиме. Здесь — как гонять его
**из файла команд**, без рук: именно так устроены домашние задачи
`pdb_needle` и `pdb_quest`.

В `demo/` три маленьких проекта: подопытный скрипт и готовый
`commands.pdb` рядом. Команды — из этой папки:

```bash
cd seminars/04-debugging
```

## 1. Post-mortem: куда ты попадаешь

```bash
uv run python -m pdb -c continue demo/01_postmortem/parse.py \
  < demo/01_postmortem/commands.pdb
```

### Почему упало

`parse.py` разбирает строки вида `"s-01:12.5"`. Одна из четырёх —
`"s-03:oops"`. `parse_value` делит её по `:`, получает `raw = "oops"` и
зовёт `float("oops")`:

```
ValueError: could not convert string to float: 'oops'
```

Исключение никто не ловит, и оно всплывает по всей цепочке: из
`parse_value` в comprehension внутри `parse_all`, оттуда в `main`, оттуда
на уровень модуля. Скрипт умирает.

`-c continue` выполняет `continue` сразу после старта pdb. Скрипт бежит до
необработанного исключения, и pdb роняет тебя **в кадр, где оно
случилось**, а не в начало файла.

### Как pdb читает команды из файла

Команды приходят на stdin, одна строка — одна команда. Три правила, и
второе неочевидное:

| Строка в файле | Что делает pdb |
|---|---|
| `p raw` | выполняет команду |
| `# что угодно` | **игнорирует**, ничего не выполняет |
| пустая строка | **повторяет предыдущую команду** |

Пустая строка — главная ловушка файлового режима. Проверено: один
пропуск между командами удваивает предыдущую, два — утраивает. Поэтому в
`commands.pdb` разделители сделаны комментариями, а пустых строк нет ни
одной.

Если команды кончились, а `q` нет — pdb выходит по EOF с кодом 0. Ставить
`q` в конце всё равно стоит: видно, что файл закончен намеренно.

### Что видно в кадре падения

| Команда | Что показывает |
|---|---|
| `where` (`w`, `bt`) | стек вызовов; включает и внутренние кадры самого pdb |
| `a` (`args`) | **только аргументы** функции: `chunk = 's-03:oops'` |
| `p <expr>` | значение выражения |
| `pp <expr>` | то же, но pretty-print |
| `pp locals()` | все локали кадра: `{'chunk': ..., 'raw': 'oops', 'sensor': 's-03'}` |
| `whatis <expr>` | тип: `<class 'str'>` |
| `l` | исходник вокруг текущей строки |
| `source <func>` | исходник функции целиком |
| `display <expr>` | напечатать и следить за значением дальше |
| `u` / `d` | вверх / вниз по стеку |

Отдельно: `retval` в post-mortem отвечает `*** Not yet returned!` —
функция не вернула значение, она упала. А `d` в самом нижнем кадре даёт
`*** Newest frame`: ниже некуда.

### Сюрприз при подъёме по стеку

`u` поднимает в `parse_all`, и там:

```
(Pdb) p chunks
['s-01:12.5', 's-02:13.0', 's-03:oops', 's-04:14.5']
(Pdb) p chunk
*** NameError: name 'chunk' is not defined
```

Аргумент функции виден, а переменная цикла comprehension — нет. С Python
3.12 comprehension не создаёт отдельного кадра, его код встроен в
функцию (PEP 709) — но переменная цикла всё равно изолирована. В стеке
отдельного кадра нет, и значения тоже нет.

Практический вывод: если упало внутри comprehension, смотреть надо в
самом нижнем кадре. Поднимешься — потеряешь то, что искал.

## 2. Условная точка останова

```bash
uv run python -m pdb demo/02_conditional/scan.py \
  < demo/02_conditional/commands.pdb
```

Скрипт складывает 50 000 показаний, одно из них `NaN`. Сумма выходит
`nan`, и **исключения нет** — NaN ничего не ломает, он просто заражает
ответ. Post-mortem тут не поможет: падать нечему.

Ставим точку останова с условием:

```
b check, reading != reading
```

`reading != reading` истинно только для `NaN` — он не равен сам себе.
pdb остановится ровно на нужном элементе, и `p index` покажет, какой это
был.

Обрати внимание: запуск **без** `-c continue`. Скрипт не падает, поэтому
pdb стартует на первой строке, мы успеваем поставить точку и только потом
делаем `c`.

## 3. `commands`, мутация локали и `restart`

```bash
uv run python -m pdb -c continue demo/03_commands_restart/collect.py \
  < demo/03_commands_restart/commands.pdb
```

Здесь битых записей три, и скрипт умирает на первой. Остальные две до нас
не доходят. Post-mortem покажет одну — и всё.

Решение целиком:

```
b read_value, record["value"] is None
commands 1
silent
p record["index"]
p record["sensor"]
record["value"] = 0.0
c
restart
c
```

Что происходит:

- **`commands N`** привязывает блок команд к точке останова N. При каждом
  попадании pdb выполнит его сам, без нашего участия.
- **`silent`** гасит стандартное «остановились там-то» — в выводе
  останется только то, что мы печатаем.
- **`record["value"] = 0.0`** правит локаль на лету. Запись починена,
  скрипт побежит дальше и дойдёт до следующей битой.
- **`c`** внутри блока продолжает выполнение автоматически.
- **`restart`** перезапускает скрипт в той же сессии. Точки останова и
  блоки `commands` переживают перезапуск — а нужен он потому, что первое
  падение случилось раньше, чем мы успели что-то поставить.

В выводе — все три записи и `сумма: 19997.0`: скрипт дошёл до конца.

Это и есть скелет решения обеих pdb-домашек.

## 4. Код объектов и байткод — коротко

Домашки `arg_binding` и `codeops` про другое: не про живой процесс, а про
устройство самого кода.

```python
def greet(name, greeting="привет", *args, **kwargs): ...


greet.__code__.co_varnames  # ('name', 'greeting', 'args', 'kwargs')
greet.__code__.co_argcount  # 2 — сколько можно передать позиционно
greet.__code__.co_flags  # биты CO_VARARGS / CO_VARKEYWORDS
greet.__defaults__  # ('привет',)
```

Из этих полей и собирается `bind_args` без `inspect`. А вложенные функции
и comprehension лежат отдельными code objects внутри `co_consts` — их
`codeops` обходит рекурсивно.

Подробно, с примерами на живых функциях `minipipe` —
в [`notebooks/introspection.ipynb`](../../notebooks/introspection.ipynb).
