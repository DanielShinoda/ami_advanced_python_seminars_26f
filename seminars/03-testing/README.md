# Семинар 3 — внутренности pytest

Лекция показала, как пользоваться pytest. Здесь — как его расширять:
хуки, scope, обмен данными между фикстурой и хуком, и как плагин попадает
в чужое окружение.

Нужно для домашней задачи `expect_log` — там пишется плагин с маркером,
проверяющим логи.

В `demo/` шесть маленьких проектов. Это обычные папки с обычными
`conftest.py` и тестами: открывай, правь, запускай заново.

Все команды ниже — из этой папки:

```bash
cd seminars/03-testing
```

## 1. Хуки и три фазы

```bash
uv run pytest demo/01_hooks -q -s
```

`@pytest.hookimpl(wrapper=True)` оборачивает фазу прогона. Имя хука
выбирает не что делать, а **когда**: `pytest_runtest_setup` — фикстуры,
`pytest_runtest_call` — тело теста, `pytest_runtest_teardown` — уборка.

В выводе видно, что обёртка охватывает именно свою фазу: `[фикстура]`
напечаталась внутри `[setup]`, тело теста — между строчками `[call]`.
А упавший тест пришёл в обёртку **исключением** — ради этого её и берут.

## 2. Вложенные conftest

```bash
uv run pytest demo/02_nested_conftest -q -s
```

Две обёртки на один хук, в двух `conftest.py`, вложенных друг в друга.
Порядок обратный ожидаемому: ближний к тесту оказался **снаружи**,
дальний внутри, тело в середине.

Причина — обёртки регистрируются по мере спуска по дереву, а последняя
зарегистрированная становится внешней.

## 3. Scope

```bash
uv run pytest demo/03_scope -q -s
```

Четыре теста в двух классах одного файла:

```
session  — 1 раз за прогон
module   — 1 раз на файл
class    — 2 раза
function — 4 раза, это значение по умолчанию
```

`autouse=True` избавляет от перечисления фикстуры в сигнатурах. Длинный
scope берут ради дорогой подготовки; цена — состояние живёт между
тестами.

## 4. Параллельный прогон

```bash
uv run pytest demo/04_xdist/test_token.py -q -rP
uv run pytest demo/04_xdist/test_token.py -q -rP -n 2
```

Один и тот же файл, одна и та же `scope="session"` фикстура. В одном
процессе — один `pid` и один секрет на все четыре теста. В двух — **два
разных**.

Воркер это отдельный процесс: свой импорт, своя память, своя сессия
pytest. Объекты фикстур между процессами не ездят. Отсюда поправка:

> `scope` означает «**не чаще** одного раза», а не «ровно один раз за
> прогон». Единица переиспользования — воркер.

`-rP` печатает вывод прошедших тестов, иначе pytest его прячет.
`worker_id` — фикстура из xdist, без параллели отдаёт `master`.

Теперь то же с тестами, которые передают состояние друг другу:

```bash
uv run pytest demo/04_xdist/test_shared.py -q
uv run pytest demo/04_xdist/test_shared.py -q -n 2
```

Последовательно — 2 прошло. Параллельно — один упал: тесты уехали в
разные процессы, и общего списка у них больше нет.

Они были сломаны и раньше. Последовательный прогон это прятал, параллель
обнаружила — а не создала.

## 5. Почему исход проверяет хук, а не фикстура

```bash
uv run pytest demo/05_fixture_cannot_fail -q
```

Фикстура роняет прогон из teardown, и получается `1 passed, 1 error`:
тест отчитался PASSED, а поверх встал отдельный ERROR. Для отчётов и CI
это разные вещи, и «упавшим» такой тест не считается.

Фикстура не знает, чем кончился тест. Хук знает — он видит исход и может
честно уронить тест в фазе `call`. Но хук не умеет просить фикстуры: он
не участвует в DI, у него нет параметров-фикстур.

Отсюда обычная для плагина связка: **фикстура собирает, хук проверяет**.

## 6. Stash

```bash
uv run pytest demo/06_stash -q -s
```

Осталось передать собранное из фикстуры в хук. Общий у них только объект
теста — `item`, и напрашивается прицепить к нему атрибут:

```python
item._my_plugin_start = time.perf_counter()
```

Работает, но так не делают: имя может занять другой плагин, `mypy`
ругнётся `attr-defined` на чужой объект, и что там лежит — никто не
знает.

У pytest для этого есть `Stash` — словарь на каждом узле (`item.stash`, а
также на `Config` и `Session`). Ключ не строка, а **объект**
`pytest.StashKey[T]()`: два плагина не столкнутся именами даже случайно, а
тип значения известен и проверяем.

Смотри `demo/06_stash/conftest.py` — это и есть скелет плагина из задачи.

## 7. Плагин в колесе

`conftest.py` работает, пока плагин нужен одному проекту. Дальше его
пакуют в wheel, и `pytest_plugins` прописывать не нужно вовсе — pytest
находит установленные плагины сам.

Механизм — entry point группы `pytest11`, тот самый `pyproject.toml` из
семинара 1:

```toml
[project.entry-points.pytest11]
maxduration = "pytest_maxduration"
```

Слева — имя, под которым плагин числится у pytest (по нему его можно
выключить: `-p no:maxduration`). Справа — модуль для импорта.

Проверить, кто уже есть в окружении:

```python
from importlib.metadata import entry_points

for ep in entry_points(group="pytest11"):
    print(ep.name, "->", ep.value)
```

Вот откуда взялись `mocker` и `--cov`.
